# Redistributable, fully inflected Hungarian lexicon for a Scrabble-style engine

## Executive finding

**Question A — can the pinned `hu_HU` be expanded correctly by a different tool?**

**There is a credible alternative expander, but I cannot certify it as correct for the pinned Hungarian dictionary without actually running the acceptance test.** The strongest candidate is **Spylls** and, specifically, its repository’s `examples/unmunch.py`. Unlike Hunspell’s old `unmunch`, Spylls parses Hunspell `AF` flag aliases, supports all four flag encodings including numeric flags, and its unmunch demo explicitly follows a first suffix into a second suffix via continuation flags. It can also expand an entire dictionary. However, its author labels the script “not extensively tested, just a demo,” it deliberately does not enumerate compounds, and I found no primary-source claim or test report saying that this script has successfully expanded Hungarian `hu_HU`. **So the defensible answer is “promising but not yet verified,” not “yes, proven.”** Spylls 0.1.7 was published 2022-01-23; canonical URL `https://github.com/zverok/spylls`; retrieved 2026-09-01. citeturn20search2turn25view2turn26view0turn26view2

The reason old `unmunch` fails is substantially clearer. The pinned LibreOffice file at commit `75f5dff8c972fff4a32e4ea8434722c277f02a3f` is Magyar Ispell 1.8.1 and uses alias-compressed Hunspell data; the Magyar Ispell build explicitly runs its `makealias` step to create compressed Hunspell dictionaries. Hunspell defines `AF` as replacing sets of affix flags with ordinal numeric aliases. Current `unmunch` source, by contrast, only recognizes `FULLSTRIP`, `PFX`, and `SFX` directives while parsing the affix file, takes only the first character of an affix-class identifier, reads the text after `/` in `.dic` entries directly, and contains no handling for `AF`, `AM`, `NEEDAFFIX`, `CIRCUMFIX`, or continuation classes. That is a direct source-level explanation for an alias-compressed `/39`-style Hungarian dictionary producing almost no expansion. **Question B — does an already-expanded artifact satisfying all five hard constraints exist?**

**I did not find one that I can certify.** The closest newly discovered artifact is Péter Rácz’s **Hungarian Webcorpus 2 Frequency List, version 1.0 (2025)**: it is fixed and versioned, contains an orthographic `form` column as well as lemmas and frequencies, is distributed as a Parquet artifact, and its GitHub repository is marked MIT. But it is a corpus-frequency inventory rather than a manually curated lexical authority, so it cannot establish that *every* retained form traces to the kind of human-curated linguistic source required by constraint 4; I also could not verify its complete diacritic inventory or the six acceptance words from metadata alone. ## Why `unmunch` fails, and what the alternatives actually do

### The immediate Hungarian-specific failure is flag-alias compression

Hunspell's format defines `AF` aliases precisely: a dictionary item can contain an ordinal such as `/1`, with `AF 1` mapping that ordinal back to the real set of affix flags. Hunspell's manual says the mechanism “substitute[s] affix flag sets with ordinal numbers.” Hunspell master manual, accompanying release 1.7.3 `c5f9815`; URL `https://github.com/hunspell/hunspell/blob/master/man/hunspell.5`; retrieved 2026-09-01. citeturn17view2

Magyar Ispell’s canonical build pipeline explicitly has an `alias` target and invokes `bin/makealias` on both its ordinary UTF-8 and morphological/generated Hunspell dictionaries. Its normal `myspell` target depends on `alias`. That is primary evidence that the distributed Hungarian dictionary is intentionally alias-compressed rather than using the raw flag vectors that an old MySpell-style expander expects. Magyar Ispell master, project release history current through 1.9.1 dated 2026-02-05; URL `https://github.com/laszlonemeth/magyarispell/blob/master/Makefile`; retrieved 2026-09-01. citeturn19search0turn13view0

The pinned `.dic` confirms the symptom from the other side: its first line is `96955`, and entries use numeric-looking slash fields instead of ordinary direct single-character affix vectors. LibreOffice dictionaries commit `75f5dff8c972fff4a32e4ea8434722c277f02a3f`, Magyar Ispell 1.8.1; URL `https://raw.githubusercontent.com/LibreOffice/dictionaries/75f5dff8c972fff4a32e4ea8434722c277f02a3f/hu_HU/hu_HU.dic`; retrieved 2026-09-01. citeturn3view1

`unmunch` does not decode that scheme. Its current parser tests only `FULLSTRIP`, `PFX`, and `SFX`; its dictionary reader splits at `/` and passes the remaining bytes directly to `expand_rootword`; and its PFX/SFX parser stores an affix class with `achar = *piece`, i.e. one character. No `AF` handling appears in the source. Hunspell 1.7.3 code lineage, current tool source; URL `https://github.com/hunspell/hunspell/blob/master/src/tools/unmunch.cxx`; retrieved 2026-09-01. citeturn18view0turn18view2turn18view3

That is enough to explain your measured result without invoking compounds or a size limit: the Hungarian stems carry aliases that old `unmunch` does not resolve to the actual suffix classes, so most roots never reach the relevant SFX rules. This is an inference from the pinned dictionary, upstream build pipeline, Hunspell format specification, and `unmunch` source rather than a claim made verbatim by one upstream document. LibreOffice commit `75f5dff8…`, Magyar Ispell 1.8.1; Hunspell 1.7.3 `c5f9815`; retrieved 2026-09-01. citeturn3view1turn19search0turn17view2turn18view0

### Even after aliases, `unmunch` is too incomplete for Hungarian morphology

Hunspell proper supports **twofold suffix stripping**, which its manual explicitly identifies as important for “agglutinative languages”; a second suffix is reached through an affix continuation class. Hunspell 1.7.3 / `c5f9815`; URL `https://github.com/hunspell/hunspell/blob/master/man/hunspell.5`; retrieved 2026-09-01. citeturn17view5

Hunspell’s own still-open expander issue is unusually strong evidence that this is not merely a theoretical concern. Issue #404 asks for a replacement for `unmunch`/`wordforms` that supports all flag types—`LONG`, `UTF`, `NUM`—and “twofold suffixes and a prefix, or twofold prefixes and a suffix.” The issue was opened 2016-09-13 and remained open when retrieved. Hunspell issue #404 against the current project, with latest release 1.7.3 `c5f9815`; URL `https://github.com/hunspell/hunspell/issues/404`; retrieved 2026-09-01. citeturn2view1

The `unmunch` source has no continuation-class handling at all, while its condition parser *does* implement Hunspell’s simplified condition syntax including `.`, positive character classes, and negated classes. So **conditions are not the main explanation for the near-zero Hungarian expansion; continuation-based two-level suffixation is a genuine additional limitation.** Hunspell 1.7.3 source; URL `https://github.com/hunspell/hunspell/blob/master/src/tools/unmunch.cxx`; retrieved 2026-09-01. citeturn18view1turn18view6

### `unmunch` is officially obsolete, and its intended replacement is still not a full solution

Hunspell’s current README calls `unmunch` **deprecated** and directs users to `wordforms`; it describes `wordforms` as the “Hunspell version of unmunch.” Hunspell 1.7.3, commit `c5f9815`, released 2026-05-05; canonical URL `https://github.com/hunspell/hunspell`; retrieved 2026-09-01. citeturn2view0turn21view0turn22search10

But `wordforms` itself is not the missing complete Hungarian expander. The same official issue #404 proposes replacing **both** old expansion tools with something that handles all flag formats and twofold affixing. The current `wordforms` script constructs direct prefix/suffix candidates and prefix+suffix combinations and then has Hunspell check them; its source does not implement an arbitrary enumeration traversal comparable to the core lookup algorithm. Hunspell 1.7.3 / `c5f9815`; URLs `https://github.com/hunspell/hunspell/issues/404` and `https://github.com/hunspell/hunspell/blob/master/src/tools/wordforms`; retrieved 2026-09-01. citeturn2view1turn15view0

### Alternative expanders and implementations checked

**Spylls 0.1.7 — strongest candidate.** Canonical URL `https://github.com/zverok/spylls`; PyPI 0.1.7 dated 2022-01-23; retrieved 2026-09-01. Its parser supports `short`, `long`, `numeric`, and `UTF-8` flag formats; understands `AF` flag-set aliases and `AM` morphological aliases; represents `NEEDAFFIX`, `CIRCUMFIX`, and `COMPOUNDRULE`; and its lookup implementation understands those constraints. citeturn20search2turn24search15turn25view2turn25view3turn25view4turn25view5turn25view6

Most importantly, Spylls is **not merely a checker** for this research question. Its repository contains a whole-dictionary `examples/unmunch.py`; the script says that omitting the single-word argument “will unmunch the entire dictionary,” applies direct suffixes, follows suffix continuation flags into secondary suffixes, and handles prefix/suffix cross-products plus secondary suffixes. Spylls repository state associated with 0.1.7-era implementation; URL `https://github.com/zverok/spylls/blob/master/examples/unmunch.py`; retrieved 2026-09-01. citeturn26view0turn26view2turn26view3

There are nevertheless two material caveats. First, its author explicitly warns that the expander is “not extensively tested, just a demo” and does not try to enumerate all compound words because that set can be unbounded. Second, the project’s license metadata is inconsistent in the material I inspected: the repository identifies MPL 2.0, while `setup.py` contains an MIT license classifier. Spylls 0.1.7; URLs `https://github.com/zverok/spylls` and `https://github.com/zverok/spylls/blob/master/setup.py`; retrieved 2026-09-01. citeturn26view0turn7view2turn24search10

### How Question A should be accepted or rejected

The appropriate acceptance test is much stronger than “the command ran.” For the exact LibreOffice source commit `75f5dff8c972fff4a32e4ea8434722c277f02a3f`, Magyar Ispell 1.8.1, retrieved 2026-09-01, the candidate expansion must contain the user-specified six forms **`házat`, `házban`, `házakat`, `kutyát`, `kutyák`, and `asztalon`** and must produce a unique alphabetic inventory on the order of **millions rather than approximately the 96,955 dictionary stems**. The latter is an acceptance criterion derived from your existing Czech/Slovak/Polish experience, not a number claimed by Magyar Ispell. Source identity for the input: `https://github.com/LibreOffice/dictionaries/tree/75f5dff8c972fff4a32e4ea8434722c277f02a3f/hu_HU`; retrieved 2026-09-01. citeturn3view1turn4view1

A second, independent sanity check should test generated standalone candidates against the same version of Hunspell’s full checker. That matters because Spylls’ demo traverses the missing suffix continuations but does not itself implement every exclusion during enumeration; for example, its standalone demo explicitly checks `FORBIDDENWORD` and `NEEDAFFIX`, while the full Spylls data model supports additional constraints such as `CIRCUMFIX` and `ONLYINCOMPOUND`. Spylls 0.1.7; URLs `https://github.com/zverok/spylls/blob/master/examples/unmunch.py` and `https://spylls.readthedocs.io/en/latest/hunspell/data_aff.html`; retrieved 2026-09-01. citeturn26view2turn25view4turn25view5

That is why my Question A verdict is **not yet “yes.”** The architecture exists and fixes exactly the two biggest deficiencies—`AF` decoding and continuation suffixes—but the six-word/million-scale Hungarian result was not available in the primary sources, and I have not invented one.

## Why Hungarian is unusually difficult here

Hungarian really is a harder-than-average Hunspell expansion target, and the difficulty is structural rather than accidental. Hunspell itself was built for languages with rich morphology and complex compounding; its manual singles out **twofold suffix stripping** as important for the “immense number of suffixes” in agglutinative languages, and its format contains Hungarian-specific language/compound handling. Hunspell's project README likewise advertises twofold affixing for Hungarian and other agglutinative languages. Hunspell 1.7.3 / commit `c5f9815`, released 2026-05-05; URLs `https://github.com/hunspell/hunspell` and `https://github.com/hunspell/hunspell/blob/master/man/hunspell.5`; retrieved 2026-09-01. citeturn2view0turn17view5turn17view1 Magyar Ispell then compresses that already rich representation through `AF` aliasing, which is entirely legitimate for Hunspell but happens to cross the capability boundary of the obsolete `unmunch` utility. Magyar Ispell 1.8.1/1.9.1 build system; URL `https://github.com/laszlonemeth/magyarispell/blob/master/Makefile`; retrieved 2026-09-01. citeturn19search0 The licensing landscape is a second, independent complication: the strongest curated spellchecking source is openly licensed, but several attractive corpus/treebank alternatives are either explicitly NonCommercial—Hungarian Webcorpus metadata and UD Hungarian-Szeged—or governed by access terms that do not provide the clear public-redistribution grant this project requires, as with the Hungarian National Corpus. Retrieved 2026-09-01. citeturn27search31turn29view5turn27search2 In other words, the proportionate next effort is **not a broad hunt for a mysterious better Hungarian list**; it is a focused empirical validation of a modern affix-aware expander against the already licensed Magyar Ispell source.
