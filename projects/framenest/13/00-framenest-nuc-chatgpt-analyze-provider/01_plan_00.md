### Findings that determine the implementation

1. The generic preparation contract enforces three frames and a 1024 px extraction edge. Its HTTP transport subsequently creates JPEGs at up to 768 px. Movie identification uses a separate five-frame contact sheet. The page provider needs its own preparation contract; changing those global constants would affect existing providers.
2. Upload is rejected by the CLI, DOM engine, extension runner, headless runner, and bridge file route. There is no hidden switch to enable it.
3. The headless job engine is a separate executor. Changing `dom_engine.js` alone would not add headless upload.
4. Generic analysis resolves providers dynamically, while movie identification captures its provider at server startup.
5. The durable coordinator discovers unfinished runs across analysis definitions but currently invokes the generic executor. Movie execution must be dispatched deliberately, without simultaneous execution from the HTTP route.
6. Movie results require exactly nine response keys, including `genres`; an empty genre list is already valid.
7. Movie metadata currently assumes `reasoning_enabled=True` and a contact sheet. Those assumptions are invalid for a browser session.
8. The copied engine can attempt a second Send click after uncertain acceptance. The new path must eliminate that replay risk.

### Budget calculation

Chosen local encoding policy:

- JPEG, RGB, metadata removed.
- Long edge **384 px**, preserving aspect ratio and never upscaling.
- Quality **65**, chroma subsampling 4:2:0.
- Maximum **128 KiB per frame**.
- Local attachment ceiling **32 MiB**.
- ZIP uses `ZIP_STORED`, generated ASCII names, fixed ZIP timestamps, and no comments, extra fields, directories, encryption, or manifest.

Let:

- `Lzip` be the successful measured or certified ZIP per-file byte bound.
- `Ltotal` be the successful aggregate-byte bound.
- `R` be the largest frame count whose ZIP was semantically read successfully.
- `B = floor(0.8 × min(Lzip, Ltotal, 32 MiB))`.
- `Nbytes` be the largest count whose worst-case JPEG payloads and exact ZIP overhead fit `B`.

For this ZIP layout, compute overhead as:

```text
22 + Σ(76 + 2 × ASCII filename length)
```

Choose the candidate operating count:

```text
N = min(Nbytes, floor(0.8 × R))
```

Then verify that exact `N` with the live semantic fixture before accepting the profile.

Composer attachment count must allow at least one ZIP. It is **not** the number of enclosed frames and must not be substituted for `R`.

A profile qualifies for video identification only if its resulting count is at least 12. This is a minimum acceptance threshold for “substantially more,” not a claimed measured count. Failure to qualify stops video enablement.

For video, sample uniformly across the full duration using bin midpoints. Preserve chronological order. If the media cannot supply the accepted temporal coverage, report a preparation limitation; never silently substitute the old three-frame or five-frame path or manufacture duplicate samples.

For GIFs, use the same measured upper budget with chronological animation sampling; fewer distinct frames, including a single frame, are valid. A still produces one image.

Validate the final archive’s actual byte size before staging. If the fixed encoding policy cannot fit, stop with a bounded preparation error; do not silently change quality or frame count.

## 5. Upload implementation and security boundary

### Reduced protocol

Use protocol version `2` on both sides. Retain only the ask lifecycle routes: health/status, executor hello/next, job creation/status/cancellation, progress, and final result.

Add:

| Operation | Behavior |
|---|---|
| `POST /v1/files` | Authenticated binary staging of one validated FrameNest derivative; returns an opaque file ID, MIME type, length, and digest |
| `GET /v1/files/{fid}` | Replaces `501`; authenticated bounded bytes for the file bound to the offered job/executor lease |
| `DELETE /v1/files/{fid}` | Idempotent cleanup of owned staged data |

Job creation references zero or one staged file ID. Analysis jobs require one; text Ping may use zero. Bind the file atomically to the job and reject reuse by an unrelated job.

Use an idempotency identity derived from analysis run, attempt, and stage. Repeated creation with the same identity must return the existing job or its terminal outcome, never a second ask.

Retain the existing JSON body bound separately from binary upload limits. Require explicit lengths, bounded reads, digest verification, and canonical MIME types.

### Component changes

| Component | Required change |
|---|---|
| `dom_engine.js` | Implement `uploadFiles()` using the measured input and attachment-state locators. |
| `job_runner.js` | Delete the extension executor; there is no second production upload path. |
| `job_engine.mjs` | Inject and call the retained DOM helper; verify prompt and attachment before one Send attempt. |
| `runner.mjs` | Fetch only the offered job’s attachment; remove the unconditional file rejection; propagate cancellation and lease cleanup. |
| `bridge_client.mjs` | Add authenticated binary retrieval, strict length/digest checks, and bounded cancellation. |
| `bridge/server.py` | Add staged-file endpoints; replace permanent `501`; reject arbitrary paths and URLs. |
| `jobs.py` | Bind file ownership, validate capability, reserve one executor, and track submission/cleanup state. |
| `results.py` | Store bounded text/error results without library, HTML, assets, or conversation archives. |
| `store.py` | Own private staging, atomic metadata, expiry, crash cleanup, and metadata-only idempotency records. |
| `cli.py` | Make `ask -f/--file FID` reference an already staged file; reject filesystem paths and multiple attachments. |

### Browser sequence

For each job:

1. Enter the configured project and create a fresh scratch chat.
2. Verify containment and clear stale composer text and attachments.
3. Insert and verify the prompt. Complete all insertion fallbacks now.
4. Fetch and verify the staged derivative through the local bridge.
5. Transfer bounded byte chunks over the owned CDP connection and construct the browser `File` in memory.
6. Assign it through the verified file input and dispatch the required input/change events.
7. Wait for a confirmed attachment-ready state; detect missing, pending, or rejected attachments.
8. Recheck the prompt, attachment count, project, and Send readiness.
9. Record the Send attempt and click **once**.
10. Observe Send acceptance and then a complete final answer. Text stability alone is insufficient while generation/tool activity remains active.
11. Clear local buffers and composer state, finish the lease, and remove staged data.

Do not call `DOM.setFileInputFiles` with arbitrary host paths. Do not put the bridge token inside page JavaScript.

If the input or completion signals do not match the measured pack, stop and re-probe. Do not send text without its required attachment.

### Security and retention

- The bridge receives derivative bytes from FrameNest’s trusted backend, never a source path supplied by a user.
- Do not expose file staging through the public FrameNest API or the ordinary web client.
- Runtime staging accepts only the generated JPEG format or the constrained JPEG-only ZIP format.
- Reject traversal, nested directories, duplicate names, symlinks, encrypted entries, ZIP64, unexpected extra data, oversized dimensions, unsupported MIME types, and decompression tricks.
- Validate image bytes and ZIP contents; an extension or declared MIME type is not sufficient.
- Use private `0700` directories and `0600` files, exclusive creation, no-follow file operations, atomic publication, and cleanup on all terminal paths.
- Disable proxy-environment use and redirects in both loopback clients. Reject any non-`127.0.0.1` endpoint.
- Require the exact Host header. Bridge machine requests use no Origin; reject requests containing a browser Origin. The separate login wizard requires its own exact same-origin checks.
- Keep attachment and text-result content transient, with a maximum one-hour expiry and bounded job count. Delete attachments promptly after completion or cancellation.
- Keep only bounded metadata needed for idempotency and unknown-outcome recovery across restart. Never persist prompts, answers, or media as a kernel archive.
- Local cleanup does not claim deletion of chats or attachments retained by ChatGPT.

On timeout or runner death, fence the owned executor before accepting another job. If cleanup cannot be confirmed, stop that browser process group and restart the managed runtime. Never kill unrelated Chromium processes.
