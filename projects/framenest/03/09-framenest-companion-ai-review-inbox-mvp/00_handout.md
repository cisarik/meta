## 7. Expert restatement of Michal’s brainstorm

This section is the product object you will plan. It is **not** yet accepted
architecture. Classify every sentence as Cooperator intent. Where repository
truth conflicts, Section 8 wins until Michal explicitly supersedes an ADR.

### 7.1 The job to be done

The ordinary website **Upload** path is for files already on disk. The
companion **Save `+`** path is how the administrator puts an X photo, GIF, or
video into FrameNest **from the browser**, without a manual download.

That ingest path already exists (W1). What is missing — and what Michal named
as the **key FrameNest companion function** — is the **admin review loop after
acquisition and real NVIDIA NIM analysis**:

1. Admin clicks `+` on X, fills Title / Tags / Description as they wish, hits
   Save (Enter should work after Worker 04).
2. Overlay closes. Bytes are acquired on the NUC. A **real** NIM API call
   analyzes the acquired object.
3. Admin **waits**. They should not have to babysit Manage media.
4. When analysis completes, the extension **notifies**.
5. The toolbar icon shows a **badge count** of unopened items that finished
   analysis.
6. Admin opens the side panel, sees a **download-manager-style list** under
   the chrome title **FrameNest**, titles only, newest analyzed items.
7. Click a row → a popup that **reuses Save overlay chrome**, but the heading
   “Save to FrameNest” is replaced by a **black dropdown** in the same green
   accent style, defaulting to the **latest** AI suggestion.
8. Admin does **not** have to accept a whole suggestion. Beside each field
   heading (Title, Tags, Description) is **✅**. They apply one field at a
   time from the suggestion currently selected in the dropdown. Tags keep **×**
   on chips; admin drops unwanted tags, then ✅ applies **only the remaining
   tags**.
9. **Save starts disabled.** Any ✅ enables it. Save writes **only the fields
   that were checkmarked**. The popup **does not close**. It then shows the
   **current stored values** and which field was taken from **which**
   suggestion (identity = API-call datetime + exact model name).
10. Suggestions are **durable**. Opening the row later still shows history.
    If the admin opens an item and takes nothing, Save stays disabled.
11. The most common apply, in Michal’s words, will be **tags**.

A second entry into the **same inbox**: from Gallery / Details **Edit**, the
existing **Analyze by AI** button runs another durable NIM call. On success
that media **also appears** in the companion list (re-analyzed), badge
included if it is new/unopened.

### 7.2 Two popups, same family, different contracts

Do not overload the current X Save overlay with review semantics.

| | **Ingest overlay** (exists) | **Review overlay** (this whole) |
|---|---|---|
| Opens from | `+` on an X tile | Inbox row under side-panel “FrameNest” |
| Header | Text “Save to FrameNest” | Black dropdown of durable suggestions |
| Fields | Title, Tags, Description | Same fields, values retarget when dropdown changes |
| Per-field ✅ | No | Yes, next to each heading |
| Save button | Enabled; submits acquisition | Disabled until at least one ✅ |
| After Save | Close; plus shows saved/failed | Stay open; show current catalog + provenance |
| Writes | Alias + first-catalog canonical seed (ADR-0065) | Explicit admin apply of chosen fields only |
| Audience | Any identity with `x.request` (Save) | **Admin only** (`analysis.run` + canonical write) |

Visual copy: reuse green `#00ff41` frame, black surface, monospace, one filled
Save, red header close. Do not invent a second visual language.

Dropdown contents, each option, must be human-readable:

- local date and time of the **provider API call** (completed run), not “now”;
- **exact model id** as stored on the run (today’s prototype constant is
  `nvidia/nemotron-3-nano-omni-30b-a3b-reasoning` per ADR-0016 — do not hardcode
  in UI if the run carries `model_id`);
- enough of the suggestion (title at minimum) to tell runs apart;
- switching the dropdown **fills the three inputs from that run** without
  writing the catalog until ✅ + Save.

While a suggestion is selected, the inputs show **that suggestion’s** title,
tags, and description so the admin can edit chips (×) **before** ✅. After
Save, the same popup shows **stored** canonical (or current admin-visible)
values, with a durable mark on fields applied from a named run.

### 7.3 Inbox list, badge, notification

**List.** Side-panel chrome, under the existing wordmark **FrameNest**, a
vertical list of titles of media that **have at least one successful durable
analysis**. Newest first. This is the “downloads” analog: not the in-page
picker, not a clone of Gallery cards.

**Badge.** Toolbar action badge = count of **unopened** items in that list.
Opening a row from this menu marks that item opened and decrements the badge.
Unopened ≠ “failed analysis”. Failed runs do not increment the success badge.
(Whether failed runs appear in a separate honest empty/error row is a Planner
question; default recommendation: list successful `analyzed` runs only;
failures stay visible in website Edit AI status.)

**Notification.** When one or more items transition to `analyzed`, the
extension shows a user-visible notification that analysis finished and items
are waiting in the FrameNest list. Wording must not claim public Gallery
publication unless Michal selected auto-publish (Section 8.4). Safer default
copy: analysis finished, ready to review.

**Permissions.** Manifest today is `sidePanel` + `storage` (+ optional
`downloads`). Badge can use `chrome.action.setBadgeText` without a new
permission. Notifications need the `notifications` permission — a **trust
expansion**. Put that in front of Michal; do not silently add it.

## 8. Binding repository traps (put these in front of Michal)

### 8.1 X acquisition currently **forbids** automatic analysis

`automatic_analysis_allowed_for_upload` in `x_acquisition.py` returns False
when the upload is linked to an X asset: **fail closed even when**
`FRAMENEST_AUTOMATIC_MEDIA_ANALYSIS_ENABLED` is true. SPEC still says X has
“no automatic AI invocation”. ADR-0044 automatic analysis is a **global
opt-in** (default false) for newly cataloged uploads; X was carved out.

Michal’s “Save then wait for real NIM” **requires a successor decision**:
allow automatic post-catalog analysis for X (admin-consented NUC flag), or
keep fail-closed and require explicit Analyze by AI (which breaks the
“wait, then notify” loop unless something else enqueues the run).

Do not silently flip the X fail-closed helper inside a UI Worker.

### 8.2 ADR-0020 vs ADR-0044 vs on-demand Edit

ADR-0020: on-demand preview is never automatic; `confirm_cloud_upload: true`
per request. ADR-0044 later accepted **optional** automatic runs after
catalog, with the **server flag** as the consent boundary for non-interactive
cloud frame upload. Interactive Analyze by AI still needs confirm.

A companion that auto-runs NIM after X Save is an ADR-0044-class enablement
**plus** lifting the X carve-out. Credentials stay server-side (`NVIDIA_API_KEY`
/ production systemd — never in the extension).

### 8.3 `companion_mutation` is still two POST routes

ADR-0061/0064: `RoutePolicy.companion_mutation` is only

- `POST /api/x/requests`
- `POST /api/x/requests/{claim_id}/retry`

Inbox list, run history, per-field apply, and “mark opened” almost certainly
need **new routes** (and likely new `companion_mutation` flags or a new
admin-only companion policy). CORS, `all_urls`, and content-script fetch of
FrameNest remain forbidden. Service worker stays the only FrameNest client.

Do not smuggle canonical writes through the existing alias PUT. Per-field ✅
that changes **Gallery/Details truth** is canonical metadata, admin-only.

### 8.4 Gallery vs inbox vs auto-publish (unresolved fork)

ADR-0049: `GET /api/media` is published-only. Cataloged ≠ Gallery.
Administrator **Manage media** already lists unpublished items
(`media.workflow.read`) and Publish is explicit
(`media.content.publish`).

Michal wants to “see it in the Gallery” after AI. Legal interpretations —
**he must pick one**:

| Id | Interpretation | Conflict |
|---|---|---|
| G1 | Inbox + Manage media is enough; ordinary Gallery after explicit Publish | Matches ADR-0049. Weakest against “videl v galerii”. |
| G2 | After successful review Save (✅ fields), auto-Publish if title+description+≥1 tag | New product; successor to 0049; dangerous if NIM junk is applied |
| G3 | After analysis **without** applying suggestions, auto-Publish because W1 already seeded metadata | Publish without a second human look at NIM; may match “wait then Gallery” if Save overlay already had tags |
| G4 | Thaw ordinary Gallery to show the admin’s own unpublished X items | Audience leak risk; conflicts 0049 public `GET /api/media` |

Predecessor recommendation: **G1 for the first implementation whole**, with
the companion inbox as the place the admin “sees” new items; Gallery stays
published-only. If Michal insists on G3 because W1 already seeded tags, that
is an explicit publication grant, not a UI detail.

Never hide auto-publish inside NUC deploy.
