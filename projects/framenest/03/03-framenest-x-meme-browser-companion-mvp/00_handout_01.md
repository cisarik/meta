## 12. Per-user alias — honest repository gap

Michal hoped this already existed and would be easy to wire into the
extension. It does not exist.

### 12.1 What exists today

PRODUCT.md: the server is authoritative for **one canonical** title,
description, and tags per media, plus **per-user visibility** (hide / trash).
Visibility is not an alias.

`media_metadata` (Alembic `0005`, later description/tag columns): primary key
is `media_id` only. One row per logical media.

`PUT /api/media/{media_id}/metadata` requires
`CAPABILITY_METADATA_CANONICAL_WRITE` (`metadata.canonical.write`). It is
**not** `companion_mutation`. Companion origin cannot call it under ADR-0061.

ADR-0023: manual-first metadata; AI drafts assist and do not own metadata.
Analyze by AI needs a catalog item, a location, and capability. X media is
not in the catalog until acquisition completes.

X import currently derives `display_title` from the claim/tweet title
(`_imported_display_title` in `x_acquisition.py`) into **canonical**
metadata.

Picker search uses catalog `display_title` and related canonical fields.

Ordinary capabilities include `x.request`. They do not include canonical
metadata write.

### 12.2 What Michal asked for

Each authenticated user has their own alias — title, tags, description — on
each saved video, GIF, and static image. Two users saving or naming the same
logical item must not overwrite each other. Canonical server metadata remains
for owner/admin/publication. The companion Save form writes the **caller's**
alias.

This is new:

- persistence (likely a new table keyed by identity + `media_id`, not a
  second write into `media_metadata`);
- domain types and validation (reuse canonical title/tag/description limits
  where they already exist);
- application service that never lets an ordinary user mutate canonical
  rows through the alias API;
- HTTP API on Tailscale identity;
- ADR for the overlay and, separately or jointly, any companion-origin
  expansion;
- picker / Gallery read policy: whose title is shown to whom;
- extension UI and message types;
- likely a pending-alias on the X claim, because the Save popup appears
  **before** a `media_id` exists.

### 12.3 The hard sequencing fact the Planner must not dodge

On X, the user names the media **before** FrameNest has cataloged it.

Analyze by AI cannot run on uncataloged bytes.

Therefore the Planner must choose an explicit lifecycle, not “open the web
form and PUT metadata”:

1. collect alias on X;
2. submit or continue an X request (today `{ url }`);
3. persist pending alias on the claim or equivalent requester-private
   record;
4. on successful import, apply the pending alias to the **per-user overlay**,
   not as a silent canonical overwrite unless Michal later chooses that;
5. only then can admin Analyze by AI target a real `media_id` / location.

If the Planner instead waits until after acquisition to show the form, it
must say so and explain the worse UX. Do not hide that fork.
