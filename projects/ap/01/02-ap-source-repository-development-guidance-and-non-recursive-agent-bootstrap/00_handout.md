## 7. Exact architecture question

The first Worker must resolve this bounded question:

> Does the AP source repository need a short root `AGENTS.md` or another smaller
> repository-local discovery mechanism to prevent a concrete development or
> agent-routing failure, while preserving `AP.md` as the sole live normative
> semantic owner and avoiding recursive self-orchestration, duplicated protocol
> text, mutable session state, stale handoffs, and confusion with consumer
> integration?

The question is not:

- whether `AGENTS.md` is fashionable or supported by many tools;
- whether every repository should have one;
- whether the old file can be modernized mechanically;
- whether AP should be renamed, marketed, expanded into APE, or repackaged;
- whether more universal protocol rules can be invented;
- whether a replacement test suite should be created;
- whether all remaining ledger items should be audited together.

The plan must identify a concrete failure model. Examples to investigate, not
presuppose, include:

- a fresh coding agent opened at the AP root does not know which files are
  semantic owners and edits projections as if they were independent owners;
- an agent treats the AP source checkout as a consuming project and runs
  `./ap init` against AP itself;
- an agent repeats broad protocol rules into prompts because no concise local
  development overlay points to the current owners;
- an agent recreates tests or stale BOOT/NEXT/WORKERS artifacts contrary to
  current lifecycle decisions;
- an agent fails to preserve executable mode, documentation projection
  consistency, or documentation-first validation boundaries;
- no concrete failure exists because existing durable documents and exact
  ORCHESTRATOR prompts already provide sufficient guidance.

Each claimed failure must be classified as observed, reproducible, structurally
inevitable, plausible but unobserved, cosmetic, or disproved. A merely plausible
benefit does not by itself justify a new durable root artifact.
