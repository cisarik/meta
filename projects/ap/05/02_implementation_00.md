## 10. Required semantics

Implement the smallest coherent version of the accepted plan §D. Do not
paste the planning report into `AP.md`. Encode meaning once in `AP.md`;
project it.

### 10.1 Dual-mode Orchestrator (not a fourth role)

An *Agent Orchestrator* is an ORCHESTRATOR instance whose client
functionally exposes session-dispatch/tool capabilities **and** whose
Cooperator-selected route (or accepted plan for that logical whole)
authorizes using them. A *Read-Only Orchestrator* lacks those
capabilities or is not authorized to use them. Both remain the
ORCHESTRATOR role. Names are descriptive capability-profile labels.
They must not become a fourth uppercase persistent role. A profile
never grants authority (RF-06).

### 10.2 Intuition boundary

Orchestrator-direct action is lawful only when all hold: inside an
accepted logical whole's routing duty; deterministic or reversible; no
AP-owner mutation; no independence claim; no substituted Cooperator
material decision; within the accepted plan.

Allowed (plan §D.2): synthesize/readiness-review Worker grants; read-only
inspection/preflight; RF-19 staging at the authorized destination and
prompt+report archival only after the report exists; create/remove a
dispatch worktree when the accepted plan or implementation grant names
that topology; emit project-owned Cooperator presentation after the
copyable English prompt; restore/clean own routing state; direct
acceptance only at evidence-ladder rung 1 for E0/E1 claims that **do not
require independence**.

Worker-required (plan §D.3): mutation of `cisarik/ap` owners or authoring
of AP content; implementation-PASS on a material candidate; any
acceptance requiring independence; publication, deployment, production;
consumer pin updates; FrameNest/NUC/credential/host/account change;
material protocol design not already locked; anything outside the
allowed list. Intuition never bypasses Plan-to-Execution (RF-04).

### 10.3 Subagent as Worker delivery

Dispatch delivers **one complete authoritative Worker prompt**
(coordinates, session target, profile, boundaries, report contract) into
one concrete session. A tool-task summary is not a prompt. The receiving
session is an ordinary AP Worker session: RF-03 and RF-19 unchanged.
One accountable WORKER per dispatched session; the dispatcher remains
ORCHESTRATOR. Default remains not-used. Authorization is the
Cooperator-selected route / accepted plan for the whole, not per-spawn
microapproval. Parallel dispatch stays under single-active default and
the bounded parallel exception. An audit is never dispatched in parallel
with implementation.

Failure: if dispatch is absent, unauthorized, or cannot deliver the
complete prompt / freshness properties, issue an ordinary copy-paste
prompt. That remains lawful. A dispatch that cannot deliver the complete
prompt is not a dispatch.

### 10.4 Independent-audit observable properties

Each checkable: `Worker session target: fresh-worker-session`; next
session ordinal; exchange `01`; zero parent conversation, shared memory,
compaction summary, or Orchestrator reasoning/implementation rationale
beyond the acceptance record inputs (candidate, owner map, allowlist,
risk claims, control matrix, governing AP, repository truth); different
concrete session from the implementer; worktree isolation never proves
independence.

**Disqualifier that must appear in `AP.md`:** a session spawned inside
the parent Orchestrator's conversation, or inheriting its conversation
history or reasoning, is not a fresh session and cannot provide
independent acceptance.

Vendor-neutral functional test (advisory examples only): the spawned
session receives only the issued prompt text as initial context, holds
no parent transcript, and returns its terminal report. Named runtimes
are non-normative.

A dispatched session that discovers parent-context inheritance stops and
reports it.

### 10.5 Recording rule

internally. Orchestrator dispatch uses existing fields only.

### 10.6 Compact synthesis

### 10.7 Opt-in signaling
