## 10. Cost-proportional reasoning contract to design

Current AP already records model, reasoning, quota, and cost constraints. The
missing question is whether those fields produce an actionable
stop-and-escalation discipline.

Design a minimal operational contract with these outcomes:

1. Default to the lowest sufficient reasoning. Medium should cover ordinary
   bounded implementation, diagnostics, documentation, and deterministic
   repairs unless a named risk requires more.
2. High requires a reason: security boundary, destructive migration,
   concurrency, publication/deployment safety, or difficult architectural
   ambiguity.
3. Extra High is exceptional: genuinely cross-cutting AP architecture or
   unresolved contradiction, not a quality badge.
4. Max requires explicit Cooperator selection. Never infer it, silently enable
   it, or recommend it merely because it is available.
5. Escalation needs a trigger. Do not move upward because progress feels slow;
   name the missing evidence or unresolved decision that the higher profile is
   expected to solve.
6. Downgrade after convergence. A high-reasoning planning result does not force
   implementation, correction, publication, or archival to use the same level.
7. Cost pressure cannot falsify evidence. If required evidence is unaffordable,
   report the limitation and offer a smaller scope; do not claim PASS.
8. Repeated reasoning is not progress. An unchanged hypothesis, unchanged
   candidate, and unchanged failing gate must not be rerun without a new causal
   action.
9. One accountable Worker by default. Do not spawn audits, corrections,
   re-audits, or publication sessions ceremonially.
10. Visible route before launch. Michal receives the model/reasoning/Plan Mode
    recommendation and exact reason before he starts the Worker.

Do not solve this with universal token counts, line limits, or currency caps.
Design a qualitative default plus project/Cooperator-configurable budget and
concrete escalation gates.

## 11. Proportional test and validation contract to design

The objective is not fewer tests at any price. It is fewer **non-causal** tests
and fewer repeated gates that do not change the decision.

Distinguish:

```text
inspection/provenance
existing focused tests
affected tests
new causal regression test
broad/full suite
runtime or testbed evidence
independent acceptance
```

Required outcomes:

1. Test breadth is selected, not inherited ceremonially. Every prompt states
   why focused, affected, broad, runtime, or independent evidence is necessary
   for this change.
2. Full suite is not an automatic Worker tax. It is required when project rules
   or change risk make it decision-relevant. Otherwise focused/affected
   evidence may be sufficient for implementation, with broader evidence
   deferred to an acceptance or publication gate.
3. Do not generate tests to appear thorough. A new test must name the uncovered
   invariant, the causal failure it detects, and why an existing test cannot
   cover it.
4. Reuse project fixtures and patterns. Do not build speculative frameworks,
   helper layers, or large synthetic matrices for a small slice.
5. Classify before fixing. Candidate defect, harness defect, environment
   defect, pre-existing failure, and acceptance limitation remain separate.
6. A new Worker-authored test can itself be defective. Import/setup/path
   failures in speculative new tests do not automatically justify code changes.
   Repair only within a bounded causal attempt; otherwise remove or park the
   speculative test and report honestly.
7. No full-suite loop. Run the broad gate once per materially changed candidate
   state. Do not rerun it after no relevant change.
8. Narrow before broad. A failing broad gate is diagnosed with the smallest
   reproducer; the broad suite is rerun only after the causal defect or
   environment condition changed.
9. Pre-existing means proven. Use exact baseline invocation and matching
   failure identity/signature when the distinction matters.
10. Non-zero remains non-zero. A mandatory non-zero gate blocks PASS. The
    response is a bounded candidate fix, environment repair, harness repair,
    changed acceptance plan, or explicit limitation — not a semantic relabel.
11. Documentation-first AP evolution remains intact. This whole must not create
    a replacement monolithic protocol suite.
12. Tests are architecture evidence, not an architecture substitute.

Specify which of these belong in semantic AP, structural prompt contracts,
operational Orchestrator/Worker projections, advisory patterns, consumer
integration, or project-owned rules.

## 12. Development freedom and environment-class contract to design

Cooperator has intentionally provided a disposable or recoverable test

- the current Orchestrator prompt may activate a named, versioned project

- activation may authorize a broad class of reversible local/testbed actions

- neither topology is universally mandatory;
- a test NUC can be classified differently from a public VPS or production host;
