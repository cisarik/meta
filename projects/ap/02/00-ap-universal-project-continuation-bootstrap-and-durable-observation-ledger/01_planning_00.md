## 5. Exact problem to prove or disprove

Current AP already defines substantial restoration semantics: dynamic fresh-Orchestrator restoration, four continuity layers, PASS/PARTIAL/BLOCKED readiness, repository and current external truth ahead of archives and private memory, non-authoritative `upgrade <canonical-repository>` ledgers, optional Discovery Records, exceptional repository handoffs, rejection of permanent BOOT/NEXT/session-state files, adaptive fresh/current routing, and optional subordinate Meta trace history.

Therefore, the problem is not “AP has no restoration rules.”

The field-evidenced candidate gap is narrower:

1. An arbitrary strong fresh Orchestrator may not have one sufficiently discoverable, executable, consumer-portable path from a minimal seed to the governing AP continuation algorithm, current project truth, active unresolved observations, and selection of exactly one next bounded logical whole.
2. A consuming project has no clearly standardized, discoverable, machine-processable storage projection for active `upgrade <canonical-repository>` observations. The ledger lifecycle and structural fields exist, but the current AP tree does not define a durable consumer storage/discovery representation.
3. As a result, continuation can still depend on an outgoing Orchestrator, private conversational memory, a long handcrafted handout, reconstruction from archived conversations, or optional Meta history.

Prove each claim from current source, narrow it, or reject it. A missing filename alone is not proof of a protocol failure.
