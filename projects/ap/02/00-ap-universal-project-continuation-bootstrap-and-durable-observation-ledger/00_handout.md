## Concrete AP problem discovered

AP already defines substantial restoration semantics:

* dynamic fresh-Orchestrator restoration;
* operational, strategic, narrative, and forward-horizon continuity;
* PASS, PARTIAL, and BLOCKED restoration dispositions;
* repository truth and current external evidence ahead of archived prompts;
* non-authoritative `upgrade <canonical-repository>` ledgers;
* optional project-owned Discovery Records;
* exceptional repository handoffs;
* rejection of permanent `NEXT_WORKER.md`, `NEXT_ORCHESTRATOR.md`, BOOT files, transcript dumps, and stale session-state databases;
* adaptive fresh/current Worker routing;
* Meta as optional historical trace rather than runtime authority.

Therefore the new problem is not simply “AP lacks restoration rules.”

The field-evidenced gap is that AP lacks a sufficiently discoverable, executable and consumer-portable projection that lets an arbitrary strong fresh Orchestrator resume an AP-integrated project after a long pause without depending on:

* the outgoing Orchestrator still being available;
* ChatGPT private memory;
* an enormous hand-written restoration prompt;
* a permanent task-specific NEXT or BOOT file;
* reconstructing a backlog from archived conversations;
* Meta being present;
* a particular model, provider, IDE, agent product, or proprietary memory mechanism.

A second connected gap is durable project ownership of unresolved analytical observations. The ledger lifecycle exists semantically in AP, but a consumer project does not yet have a clearly standardized, discoverable and machine-processable storage projection for its active observation ledger.

This currently leaves important unresolved observations dependent on conversational memory or on a manually synthesized outgoing handout.

## COOPERATOR intent

The COOPERATOR wants AP to become a genuinely universal development protocol suitable for all his future projects.

A future strong model should be able to resume an AP-integrated project, deeply inspect its current code and evidence, interact with the COOPERATOR, and identify the highest-value next bounded work. Examples include:

* meaningful product capabilities;
* data-integrity or security improvements;

* architectural simplification;

* dependency, Python, database, or module upgrades;

* UI/UX work when it is genuinely the highest-value remaining objective.

This must come from current evidence, not from manufacturing work merely to exercise AP.

FrameNest remains the primary proving ground after the AP change is published and adopted.

## Design hypotheses, not predetermined answers

Treat the following as hypotheses to test, not implementation instructions.

### Hypothesis A — universal continuation projection

AP may benefit from a durable operational projection such as:

```text
CONTINUATION.md
```

or an equivalently discoverable artifact.

Its function would be to tell any fresh Orchestrator how to reconstruct an AP-integrated project. It would contain a stable algorithm and evidence contract, not the current Worker, current task, latest prompt, repository backlog, or mutable session state.

The Plan Worker must determine whether:

* a new AP-level file is justified;
* existing `AP_ORCHESTRATOR.md`, `PROMPT_CONTRACTS.md`, `INTEGRATION.md`, or another owner should instead be extended;
* a new file would duplicate semantic ownership;
* the artifact should be linked from the managed `AGENTS.md` block;
* the `ap` utility should expose or validate it;
* its name should be `CONTINUATION.md`, something more explicit, or no new file at all.

Do not force the filename before analysis.

### Hypothesis B — durable project observation ledger

An AP consumer may need a project-owned durable file containing unresolved analytical observations with stable identities and lifecycle fields.

It must remain non-authoritative discovery input. It must not become:

* a roadmap;
* an issue tracker replacement;
* a current task prompt;
* a Worker registry;
* a transcript;
* a decision authority;
* a second specification;
* a permanent NEXT file;
* a hidden model-memory dump.

The Plan Worker must determine:

* exact semantic ownership;
* whether AP should standardize storage or only a schema/discovery contract;
* the appropriate project-local path;
* how it is discovered through `AGENTS.md`, `ap.project.conf`, or another integration surface;
* whether the file is required or optional;
* how multiple canonical-repository ledgers are represented;
* whether the existing exact name `upgrade <canonical-repository>` maps into file sections, records, separate files, or another representation;
* stable record identifiers;
* lifecycle states;
* evidence and provenance;
* observed-at and last-revalidated commits;
* invalidation conditions;
* dependencies and exclusions;
* promotion into ADRs, specifications, roadmaps, issues, or active logical wholes;
* terminal reconciliation and retention through Git history;
* how private conversational memory becomes safely disposable only after committed reconciliation.

### Hypothesis C — minimal universal continuation seed

A future AP-integrated project may be resumable from a very small stable human instruction conceptually similar to:

```text
Resume this AP-integrated project.
Read the root AGENTS.md and the pinned AP continuation contract.
Begin read-only.
Restore canonical state, reconcile the project observation ledger,
and select exactly one bounded next logical whole with the COOPERATOR
before granting mutation authority.
```

The Plan Worker must determine whether this can truly be universal and how a fresh agent discovers every required input without copying protocol semantics into the seed.

### Hypothesis D — two-stage continuation

The continuation lifecycle may need to distinguish:

1. project restoration/bootstrap;
2. selection and handoff of one concrete logical whole.

This conceptual separation is likely valuable.

However, Meta filenames such as:

```text
00_handout.md
01_planning_00.md
01_report_00.md
```

are Meta-local storage policy. They must not become universal AP semantics.

### Hypothesis E — COOPERATOR routing capsule

Human-facing routing instructions are useful after a complete generated prompt:

* fresh versus current session;
* recommended reasoning depth;
* Native Plan Mode state;
* exact Meta archive path.

These should remain outside the authoritative Worker prompt unless the corresponding field belongs to the AP prompt contract.

The COOPERATOR’s current visual convention is:

* `🆕` means a fresh session;
* `♻️` means the current session;
* `💡` appears only when Native Plan Mode must be enabled or retained;
* no lightbulb appears when Native Plan Mode is off;
* reasoning recommendation appears after the complete prompt;
* archive paths appear after the complete prompt.

The Plan Worker must determine whether AP needs a vendor-neutral routing-record concept or whether this is correctly a project/Orchestrator presentation convention.

Do not encode emoji as universal protocol semantics.
